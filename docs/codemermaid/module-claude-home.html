concept

One job: resolve a directory

claude_home does exactly one thing — it answers "where is ~/.claude?" The default is $HOME/.claude, but the OHMYC_CLAUDE_HOME env var overrides it. That's the whole module. It doesn't read files, doesn't write files, doesn't parse anything. It returns PathBuf values.

The reason this is a separate module instead of a constant: testability. Every test in the crate sets OHMYC_CLAUDE_HOME to a temp directory before running. Without the env-override pattern, tests would either need to mock the filesystem or touch the real ~/.claude — both bad options. This module's simplicity IS its value.

The resolve function

crates/ohmyc-core/src/claude_home.rs 
1pub fn resolve() -> Result<PathBuf, ApiError> {2    if let Ok(override_path) = std::env::var(ENV_OVERRIDE) {3        if !override_path.is_empty() {4            return Ok(PathBuf::from(override_path));5        }6    }7    let home = dirs::home_dir()8        .ok_or_else(|| ApiError::Internal("could not determine home dir".to_string()))?;9    Ok(home.join(".claude"))10}
L2

Check OHMYC_CLAUDE_HOME first. This is the testability escape hatch — every unit test sets this to tempfile::tempdir() so tests never touch the real ~/.claude.

L3

Empty-string guard: OHMYC_CLAUDE_HOME="" should fall through to the default, not resolve to the current working directory.

L7–8

Fallback: use the dirs crate to find $HOME. The ok_or_else converts None into ApiError::Internal — rare but possible on containers or minimal systems.

concept

Convenience helpers

The module also provides join(rel) (resolve + append a relative path), plugins_dir(), and settings_path(). Each is a one-liner built on resolve(). The pattern is worth noticing: the helpers compose on the single source of truth (resolve()) instead of each computing its own path. If the resolution logic ever changes, every helper follows automatically.

Why does resolve() check for an empty string after reading the env var?
AAn empty env var should fall through to the default ~/.claude, not resolve to the current working directory

DIt's a performance optimization to avoid unnecessary path construction
Correct: A — PathBuf::from("") is valid Rust and resolves to the current directory. If a user accidentally sets OHMYC_CLAUDE_HOME="", the system would look for ./agents, ./settings.json, etc. in the CWD — silently wrong behavior. The empty-string guard prevents this. B is wrong (no panic). C is wrong (dirs is not involved when the env var is set). D is wrong (not about performance).
takeaway

claude_home is the crate's simplest module by design — it does one thing (resolve ~/.claude) and does it correctly for both production (default path) and testing (env override). Every module that reads from or writes to ~/.claude depends on this single source of truth. The env-override pattern is the testing foundation for the entire crate.
