The Profile struct and CRUD

A profile is a JSON file at $OHMYC_HOME/profiles/<name>/profile.json. It declares which agents, skills, commands, and plugins the profile uses, plus optional model config, hooks, MCP servers, LSP servers, and settings overrides. The crud submodule provides pure file I/O: list, get, create, update, delete. No symlinks, no settings mutation — those belong to activation.

The active profile is tracked in $OHMYC_HOME/profiles/.active — a plain text file containing the profile name. When a profile is activated, the name is written to this file. The read_active_profile_name function handles both relative names and absolute paths (from legacy formats).

concept

Transactional activation

Profile activation is the most complex operation in the crate. The activation.rs file is ~800 lines. The process: read the profile JSON, resolve all component references, symlink agents/skills/commands into ~/.claude, merge plugin lists, deep-merge settings, inject environment variables for model configs, and write the active marker. Every mutation is recorded on an undo stack. If any step fails, rollback() replays all previous mutations in reverse.

1enum UndoAction {2    RemoveFile(PathBuf),3    RemoveDir(PathBuf),4    RestoreInstalled(Value),5    RestoreKnown(Value),6    RestoreSettings(Option<Vec<u8>>),7}89fn rollback(actions: &[UndoAction], plugins_dir: &Path, claude_settings_path: &Path) {10    for action in actions.iter().rev() {11        action.run(plugins_dir, claude_settings_path);12    }13}
L6

RestoreSettings(Option<Vec<u8>>) captures the pre-activation state: Some(bytes) if settings.json existed, None if it didn't. On rollback, Some restores the file, None removes it — preventing an empty orphan file.

L9–10

.rev() — reverse iteration is the key to compensating transactions. If the activation completed steps 1-5 and failed on step 6, rollback undoes step 5, then 4, then 3, then 2, then 1.

whoa · code

Saga-pattern transactions for plain filesystem operations

The activation engine implements the saga pattern at the filesystem level. Each step records a compensating action, and on failure, the compensating actions run in reverse. This is the same pattern used in distributed systems for multi-service transactions, but here it's applied to a single machine's filesystem. The reason: Claude Code reads its config as flat files, so there's no database to provide ACID guarantees. The undo stack is the only way to guarantee atomicity.

Preflight: the dry-run preview

Before activation, the UI calls preflight::check() to get a preview of what will happen. The preflight module simulates the activation without writing anything: it checks which components are missing, whether settings will conflict, and what environment variables will change. The result is a structured report the UI renders as a confirmation dialog.

Preflight is read-only — it never touches the filesystem. This separation (check first, then activate) is the same pattern as terraform plan before terraform apply.

concept

RAII file locking

The lock.rs submodule provides a RAII LockGuard using fs2::FileExt for cross-process exclusive locking. When activation starts, it acquires a lock file to prevent concurrent activations from corrupting state. The lock is released automatically when the LockGuard is dropped — even if the activation panics.

Why does RestoreSettings use Option<Vec<u8>> instead of just Vec<u8>?
ATo support restoring either JSON or binary content
BTo reduce memory usage when the file is empty
CNone means settings.json didn't exist before activation — on rollback, the file should be removed, not overwritten with empty bytes
DTo distinguish between the file existing and being empty
Correct: C — If settings.json didn't exist before activation, the rollback should remove the file (not leave an empty JSON object). None captures "file didn't exist" and triggers removal on rollback. Some(bytes) captures the previous content for restoration. A is wrong (it's always JSON). B is wrong (not about memory). D is close but the distinction is existence, not emptiness.
takeaway

The profiles module is the crate's transaction engine. The Profile struct declares what a profile wants. The CRUD layer manages profile JSON files. The activation engine performs multi-file mutations with an undo stack that replays in reverse on failure — the saga pattern applied to plain filesystem operations. Preflight provides dry-run previews. RAII file locking prevents concurrent activations. Together, these components make it safe for OhMyC to write into ~/.claude — a directory it doesn't own.
