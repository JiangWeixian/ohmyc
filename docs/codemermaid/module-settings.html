concept

Three-way read result

The read() function returns a SettingsRead struct with three fields: path (the resolved file path), content (parsed JSON or None), and exists (boolean). The three possible states are: file exists with valid JSON (exists: true, content: Some(...)), file missing (exists: false, content: None), or file malformed (ApiError::Parse).

Why not just return Option<Value>? Because the UI needs to distinguish "settings file doesn't exist yet" from "we couldn't read it." Missing means "show defaults"; parse error means "show an error message."

Atomic write via temp-file + rename

L2–3

Reject non-object content upfront. Settings must be a JSON object — arrays, strings, and null are all invalid. This matches the TypeScript server's validation.

L10

to_string_pretty — the file is human-readable JSON. Users may open settings.json in a text editor, so pretty-printing matters.

L11–14

The atomic write pattern: create a temp file in the same directory, write content to it, then persist() (which calls rename()). Same-directory is important — rename only works atomically within the same filesystem.

concept

The "missing is not an error" pattern

The read() function treats settings.json not existing as valid state (exists: false). This is the same pattern used in components (missing directory → empty list) and store/provenance (missing index → empty map). The invariant: a missing config file is the "no configuration yet" state, not a system error.

quiz

Check your understanding

Why does the temp file need to be created in the same directory as the target file?
ATo avoid polluting the system temp directory
BBecause rename() only works atomically within the same filesystem, and temp directories may be on different mounts
CTo ensure correct file permissions on the temp file
DTo make cleanup easier if the process crashes
Correct: B — rename(2) fails with EXDEV if source and destination are on different filesystems. By creating the temp file in the same directory, we guarantee they're on the same filesystem and the rename is atomic. A is a minor benefit but not the reason. C is wrong (permissions follow the file, not the directory). D is wrong (NamedTempFile handles cleanup).
takeaway

The settings module provides atomic read/write for settings.json. The three-way read result distinguishes missing, valid, and malformed states. The write function uses temp-file + same-directory rename for single-file atomicity. The "missing is not an error" pattern is consistent across the crate — missing config is valid state, not a system failure.
