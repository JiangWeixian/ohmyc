The read path: bytes to structs

Every read follows the same pipeline: resolve path → read bytes → parse into serde_json::Value or a typed struct → return. The path comes from claude_home or store. The reader (components, settings, plugins) opens the file, handles the "file vanished between listing and read" case (read_md_or_skip), and parses. Malformed data becomes ApiError::Parse; missing files become Ok(None) or Ok(exists: false).

Watch the pattern — every reader normalizes "file not found" into a non-error result. That's because in a directory-tree config system, files appear and disappear as the user edits. A missing file is valid state, not exceptional.

The write path: structs to atoms

Writes are rarer and more dangerous. The settings module uses the temp-file + atomic rename pattern: serialize to JSON, write to a sibling temp file, then rename() the temp file over the target. On most filesystems, rename is atomic — the reader never sees a partially-written file.

The profiles/activation write path is more complex — it performs multiple writes (symlink agents, write plugin JSONs, merge settings, inject env vars). Each write records an UndoAction on the stack. If any write fails, rollback() reverses all previous writes. The result is multi-file atomicity without a database.

Check your understanding

Why does settings::write use a temp file + rename instead of writing directly to settings.json?
ATo improve write performance by buffering in memory first
BTo prevent readers from seeing a partially-written file — rename is atomic on most filesystems
CTo avoid locking the file while writing
DTo create a backup before overwriting
Correct: B — If the process crashes mid-write, a direct write leaves a corrupt file. Temp-file + rename guarantees the reader either sees the old content or the new content — never a partial write. A is wrong (no performance benefit). C is wrong (the crate uses fs2 for locking elsewhere). D is wrong (no backup is kept — the old file is overwritten).
takeaway

Data flows in two directions. The read path normalizes missing files into non-errors and parses bytes into typed structs at the module boundary. The write path uses atomic single-file writes (temp + rename) and multi-file compensating transactions (undo stack) to guarantee consistency. The error module's ApiError enum is the shared vocabulary — every module converts its domain-specific failures into the same tagged shape.
