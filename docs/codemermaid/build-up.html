Capability 1: Know where files live

Before the system can read, write, or watch anything, it needs to answer one question: where are the files? That's the entire job of the Path Resolution layer. claude_home::resolve() returns ~/.claude (or the env override), and store::base_dir() returns $OHMYC_HOME. Everything else in the crate is built on top of these two functions.

The move is simple but intentional — by making path resolution a function instead of a hardcoded constant, every consumer becomes testable with temp directories. Every test in the crate sets OHMYC_CLAUDE_HOME or OHMYC_HOME to a temp path, runs the code under test, and restores the env var on cleanup.

The resolve function

crates/ohmyc-core/src/claude_home.rs

L2–3

Env var check first — if OHMYC_CLAUDE_HOME is set and non-empty, it wins. This is the testability escape hatch: every unit test sets this to a temp directory.

L3

The empty-string guard matters — an env var set to "" should not override the default. Without this check, OHMYC_CLAUDE_HOME="" would resolve to the current directory.

L7–8

Fallback: use the dirs crate to find $HOME, then append .claude. The ok_or_else converts None into ApiError::Internal — rare but possible on systems without a home directory configured.

Capability 2: Read structured content from disk

With paths resolved, the next capability is parsing files into structured Rust types. The components module reads .md files from ~/.claude/{agents,skills,commands}/ and returns typed structs like Agent, Skill, and Command. Each of these has a frontmatter field (parsed YAML) and a content field (the body after the --- delimiter).

The interesting design choice: files without the required name and description fields are silently skipped, not errored. That's because ~/.claude/agents/ might contain README files, templates, or other non-agent markdown. The readers filter rather than reject — the caller gets only valid components.

Similarly, settings reads settings.json with a three-way result: file exists with valid JSON, file missing (returns exists: false), or file malformed (returns ApiError::Parse). Missing is not an error — it's the "no settings yet" state.

L8

gray_matter is lenient — malformed YAML can deserialize without error but produce Null. This boundary check catches that case so callers never see a null frontmatter.

L9–12

Null rejection: the "loud at the boundary" pattern. If YAML between --- delimiters is empty or unparseable, this fails immediately rather than letting every downstream .get("name") silently return None.

L21

No frontmatter at all? That's fine — return an empty JSON object. A markdown file without YAML frontmatter is still valid content; it just has no metadata fields.

Capability 3: Safely delete with reference checks

Once components can be listed and profiles can reference them, a new problem appears: what happens when you delete a component that a profile depends on? The answer is the store/references module. Before any delete, the system scans every profile's profile.json for references to the target component. If any profile lists it, the delete is blocked with a ReferencedBy error that includes the list of dependent profiles.

This is the "safe-delete gate" pattern — it prevents data corruption by checking the dependency graph before a destructive operation. The UI reads the referencedBy array from the error response to show the user which profiles would break, and offers a force-delete option that bypasses the check.

Reference scanning

1pub fn referencing_profiles(2    profiles_dir: &Path,3    kind: ComponentKind,4    component_name: &str,5) -> Result<Vec<String>, ApiError> {6    if !profiles_dir.exists() {7        return Ok(Vec::new());8    }9    let mut out: Vec<String> = Vec::new();10    for entry in std::fs::read_dir(profiles_dir).map_err(ApiError::from)? {11        let entry = entry.map_err(ApiError::from)?;12        let p = entry.path();13        if !p.is_dir() { continue; }14        let dir_name = match p.file_name().and_then(|s| s.to_str()) {15            Some(s) if !s.starts_with('.') => s.to_string(),16            _ => continue,17        };18        let profile_path = p.join("profile.json");19        let raw = match std::fs::read_to_string(&profile_path) {20            Ok(s) => s,21            Err(e) if e.kind() == std::io::ErrorKind::NotFound => continue,22            Err(_) => continue,23        };24        let profile: Value = match serde_json::from_str(&raw) {25            Ok(v) => v,26            Err(_) => continue,27        };28        // ...match check and push to out...29    }30    out.sort();31    Ok(out)32}
L6–7

Missing profiles directory is not an error — it means no profiles exist, so no references can exist. Early return with an empty vec keeps the caller's logic simple.

L13

Only scan directories — regular files in the profiles dir are not profiles. Each profile is a subdirectory containing profile.json.

L15

Skip dot-prefixed directories (like .active). These are internal state files, not profile directories.

L20–22

Defensive reads: NotFound is benign (profile dir without a JSON file), and other read errors are also skipped. This keeps the scan resilient — one corrupted profile doesn't block the reference check for all others.

L25–26

Malformed JSON? Skip it. The scan is tolerant because its job is to find references, not validate profiles. A profile that can't parse can't reference anything meaningful.

Capability 4: Activate a profile transactionally

Now the system has paths, readers, and safety checks. The next capability is the big one: activating a profile. This is where the profiles module reads a profile's JSON, resolves all its component references, symlinks agents/skills/commands into ~/.claude, merges plugins and settings, injects environment variables for model configs, and writes the result — all as a single transaction.

If any step fails (a component is missing, a write fails, a symlink breaks), the rollback() function replays every completed mutation in reverse order. The undo stack tracks file removals, directory removals, plugin restores, and settings restores. This is file-level compensating transactions — the only option when you're orchestrating plain files on disk without a database.

Undo stack in action

crates/ohmyc-core/src/profiles/activation.rs 
1#[derive(Debug)]2enum UndoAction {3    RemoveFile(PathBuf),4    RemoveDir(PathBuf),5    RestoreInstalled(Value),6    RestoreKnown(Value),7    RestoreSettings(Option<Vec<u8>>),8}910fn rollback(actions: &[UndoAction], plugins_dir: &Path, claude_settings_path: &Path) {11    for action in actions.iter().rev() {12        action.run(plugins_dir, claude_settings_path);13    }14}
L3

RemoveFile — recorded after every file creation (symlink, plugin JSON write). On rollback, this removes the file that was just created.

L5

RestoreInstalled — captures the previous content of installed_plugins.json before activation overwrites it. On rollback, it writes the old content back.

L7

RestoreSettings — captures Option<Vec<u8>>: Some(bytes) means settings.json existed before and should be restored; None means it didn't exist and should be removed on rollback.

L11

The key move: .rev() — play actions in reverse order. If step 5 fails, undo steps 4, 3, 2, 1 in that order. This mirrors database transaction rollback semantics but at the filesystem level.

whoa · architecture

File-level compensating transactions instead of a database

Most apps would put profiles and component references in a database and use ACID transactions for activation. ohmyc-core can't — it's managing ~/.claude, a directory tree owned by a different application (Claude Code). The only way to configure Claude Code is to write files into its directory structure. So the transaction engine uses compensating actions — record every mutation, reverse on failure. This is the saga pattern applied to plain filesystem operations. It's more complex than a database transaction, but it's the only correct approach when you don't own the storage format.

Capability 5: Query the timeline

The final capability is reading data from Claude Code's SQLite database. The timeline module queries ~/.claude/timeline.db for session events, project statistics, heatmaps, and status information. It's a read-only module — it never writes to the database.

This is where the crate crosses from file I/O into structured querying. SQLite provides its own transaction guarantees, so the timeline module doesn't need the undo-stack pattern. It opens a connection, executes parameterized queries, and returns typed results.

Together with the watcher module (which emits FsEvent::TimelineDb when the database file changes), the timeline queries enable the UI to show real-time session history without polling.

takeaway

The system grows from a single path resolver into a complete filesystem management engine in five capability increments: path resolution, structured file reading, safe-delete reference checking, transactional profile activation, and SQLite timeline querying. Each capability builds on the ones below it, and the undo-stack transaction engine is the architectural peak — it's what makes it safe for OhMyC to write into a directory tree owned by another application. The watcher module adds real-time reactivity, completing the picture.
