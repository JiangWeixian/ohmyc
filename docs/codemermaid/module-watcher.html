concept

Typed filesystem events

The watcher emits two event types via the FsEvent enum: TimelineDb (the SQLite database changed) and ClaudeHome (a file in ~/.claude changed). The Tauri layer receives these events and forwards them to the frontend as fs:changed messages, triggering UI refreshes.

The classification is simple but intentional: the frontend needs to know what kind of data changed — timeline data or config data — so it can refresh the right panel without querying everything.

Path-based event classification

crates/ohmyc-core/src/watcher.rs 
1let mut debouncer = new_debouncer(Duration::from_millis(250), move |res| {2    let Ok(events) = res else { return };3    for ev in events {4        let p = &ev.path;5        let path = p.to_string_lossy().into_owned();6        if !matches!(ev.kind, DebouncedEventKind::Any) {7            continue;8        }9        let lower = path.to_lowercase();10        let event = if lower.ends_with("timeline.db")11            || lower.ends_with("timeline.db-wal")12            || lower.ends_with("timeline.db-shm")13        {14            FsEvent::TimelineDb { path }15        } else {16            FsEvent::ClaudeHome { path }17        };18        let _ = tx.send(event);19    }20})
L8

Only process DebouncedEventKind::Any events — generic file changes. Other event kinds (create, delete, etc.) are filtered out to reduce noise.

L9

Case-insensitive comparison (to_lowercase()) — the path might be Timeline.DB on case-insensitive filesystems (macOS).

L10–12

Three suffixes: .db (main database), .db-wal (write-ahead log), .db-shm (shared memory). SQLite uses WAL mode, so changes appear in these auxiliary files too.

L14, L16

Binary classification: timeline DB file → TimelineDb, everything else → ClaudeHome. Simple, but sufficient — the frontend only needs to know "should I refresh timeline data or config data?"

concept

Debounced 250ms window

The watcher uses notify-debouncer-mini with a 250ms debounce window. When a file changes, the debouncer waits 250ms for additional changes before emitting an event. This prevents burst events — a single file save might trigger multiple low-level notifications (write, flush, metadata update), and the debouncer collapses them into one event.

The 250ms value is a tradeoff: fast enough to feel responsive in the UI, slow enough to absorb filesystem noise.

concept

Lifecycle: keep the debouncer alive

The spawn() function returns Debouncer<RecommendedWatcher> — the caller must keep this value alive. Dropping the debouncer stops the watcher thread. This is an RAII pattern: the debouncer's lifetime controls the watcher's lifetime. The Tauri layer stores the debouncer in application state to keep it alive for the entire app session.

Non-existent paths are skipped during setup — the watcher only registers paths that exist. This prevents errors when watching a directory that hasn't been created yet.

Check your understanding

Why does the watcher check for .db-wal and .db-shm suffixes in addition to .db?
ASQLite in WAL mode writes to auxiliary files — the main .db file may not change during normal operations, so watching only it would miss most database updates
BThey are backup files that indicate a database corruption
CThe watcher needs to track all files in the directory, including temporary ones
DIt's a fallback in case the main database file is locked
Correct: A — SQLite's WAL (Write-Ahead Logging) mode writes changes to .db-wal and tracks shared memory in .db-shm. The main .db file is only updated during checkpointing. Without watching these auxiliary files, the watcher would miss most database writes. B is wrong (WAL files are normal, not corruption). C is wrong (the watcher only cares about these specific suffixes). D is wrong (not about locking).
takeaway

The watcher is the crate's real-time edge. It classifies filesystem events into two types — timeline database changes and config changes — using path suffix matching. The 250ms debounce window absorbs filesystem noise while staying responsive. The RAII lifecycle pattern means the caller controls the watcher's lifetime by holding the debouncer. Watching .db-wal and .db-shm files ensures SQLite WAL-mode writes are detected.
