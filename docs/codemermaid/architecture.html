Four layers, one crate

ohmyc-core is a layered library crate — not a microservice, not a framework. Every module lives at one of four conceptual layers, and the dependency rule is strict: a layer only imports from layers below it, never above. The layers, from bottom to top:

Path Resolution — claude_home and store know where files live on disk. They do not read or write content; they return PathBuf values.

File Readers — components, plugins, settings, and configs take paths from the resolution layer and read + parse files. They return structured Rust types (Agent, SettingsRead, etc.) but never mutate state.

Core Logic — profiles and timeline orchestrate reads, writes, and transactions. The profiles module is the largest and most complex — it owns a transactional activation engine with an undo stack.

Event Layer — watcher sits at the edge. It watches filesystem paths and emits typed FsEvent variants. It does not import from core logic; it only receives paths to watch.

Notice the tradeoff: by keeping the crate as a pure library with no Tauri imports, every module is unit-testable with temp directories. That's why you see ENV_LOCK mutexes and tempfile::tempdir() throughout the tests.

Path resolution: two roots

Watch this — the crate manages two separate directory trees. claude_home resolves ~/.claude (overridable via OHMYC_CLAUDE_HOME). This is where Claude Code stores its own config: agents, skills, commands, settings, plugins, and the timeline SQLite database.

store resolves $OHMYC_HOME (default ~/.config/ohmyc/). This is OhMyC's own directory — imported agents, skills, commands, model configs, and profiles. The separation is deliberate: OhMyC never writes directly into ~/.claude during CRUD operations. It only touches ~/.claude during profile activation, when it needs to symlink or copy components into Claude Code's directories.

Why two roots? Because Claude Code owns ~/.claude. OhMyC is a manager on top — it needs its own staging area where it can safely import, organize, and preview components before writing anything into Claude Code's config.

The transactional activation engine

Here's where it gets clever. Profile activation in profiles/activation.rs is a transactional state machine that performs 10+ filesystem operations (symlink agents, write plugins, merge settings, inject env vars) — and if any step fails, it rolls back every previous step using an undo stack of UndoAction variants.

The undo stack records every mutation as it happens: RemoveFile(path), RemoveDir(path), RestoreInstalled(previous_value), RestoreSettings(previous_bytes). On failure, rollback() replays the stack in reverse order. This is not a database transaction — it's file-level compensating actions, which is the only option when you're orchestrating plain files on disk.

The preflight module (profiles/preflight.rs) adds another safety layer: a dry-run that checks whether all referenced components exist, whether settings will conflict, and what environment variables will change — without writing anything. The UI calls preflight before activation to show the user a preview.

takeaway

ohmyc-core is a layered Rust library with strict dependency direction: path resolution feeds file readers, file readers feed core logic, and the event layer sits at the edge. The two-root design (~/.claude vs $OHMYC_HOME) keeps OhMyC's staging area separate from Claude Code's live config. The profiles module is the heart of the system — a transactional activation engine with undo-stack rollback and preflight dry-runs. Once you see this four-layer shape, every module's responsibility lines up.
