02 · Kimi Code

Moonshot AI
5h 窗口：有（滚动） 周额度：仅旧套餐 月度总额度：有（会员共享）

额度结构

  • 新套餐（2026 现行）：周额度已移除，只保留滚动 5 小时限速窗口——短时间请求过多触发限流，窗口滚过后自动恢复；另有 Kimi 会员共享的月度总额度，用尽则冻结至月度重置或升级。
  • 旧套餐（存量不受影响）：周额度从订阅日期起每 7 天自动刷新，未用完不结转，同样叠加 5h 窗口。
  • 所有登录设备与 API Key 共享同一额度；超额后可启用 Extra Usage（人民币余额按量计费）。

查询方式

  • Kimi Code Console 网页：可随时查看剩余额度与限流状态；5h 或周额度用到 80% 以上时进度卡出现 Buy Extra Usage 入口。
  • CLI /usage 命令：显示 token 用量、上下文消耗与额度信息。
  • /usage 背后的云端接口（逆向自本机 CLI 二进制 ~/.kimi-code/bin/kimi，已实测无凭证返回 401 确认存在）——你的推断正确，CLI 确实是请求了接口：
GET https://api.kimi.com/coding/v1/usages   # 国际区：api.kimi.ai
Authorization: Bearer <access_token>   # 订阅 OAuth token 或 Kimi For Coding API key 均可

# 响应字段（取自 CLI 内置的解析器 packages/oauth/src/managed-usage.ts）：
#   usages.limit_5h / limit_7d / limit_month_total / limit_month_code
#     各含 { used_ratio (0–1), reset_time } —— 重置时间由 API 直接返回，无需推算
#   boosterWallet —— Extra Usage 余额（amount/amountLeft 为定点数，÷10⁶ = 美分）
# 注：新套餐已取消周额度，limit_7d 应缺省；CLI 本地 server 模式另有 GET /oauth/usage 同源代理
来源 Kimi Code 官方文档 — Membership · Slash Commands 参考 · 本机 CLI 二进制逆向（packages/oauth/src/managed-usage.ts 编译产物）+ /usages 端点实测 401

03 · Gemini / Antigravity

Google
5h 窗口：仅 Antigravity 周额度：仅 Antigravity Gemini CLI：纯日额度 月度配额：没有
重大背景 2026-06-18 起，个人订阅（免费档 / AI Pro / AI Ultra）已从 Gemini CLI 迁移到新的 Antigravity CLI（agy）；Gemini CLI 只剩企业许可与 API key 用户。两条线是两套完全不同的计量体系。

Antigravity 线（个人订阅的实际载体）— 5h + 周双窗口

  • 配额桶：gemini-5h、gemini-weekly、3p-5h（第三方模型 5h）、3p-weekly；Pro/Ultra 每 5 小时滚动刷新直至周上限，免费档仅周配额（每周刷新一次）。消耗按 agent 工作量加权，不按固定请求数。
  • 官方 statusline 契约（唯一文档化的机器可读通道）：在 ~/.gemini/antigravity-cli/settings.json 配置 statusLine.command 后，agy 每次状态变化向脚本 stdin 推送 JSON，其中 quota 对象按桶给出 remaining_fraction、reset_time（ISO-8601）、reset_in_seconds，另有 plan_tier 等字段。
  • 逆向端点：POST https://cloudcode-pa.googleapis.com/v1internal:retrieveUserQuotaSummary（agy /usage 面板背后端点）；凭证在 macOS Keychain（gemini/antigravity 条目）或 ~/.gemini/oauth_creds.json。

Gemini CLI / Code Assist 线（企业许可）— 纯日额度

  • 日额度：个人 1,000 请求/天、Pro 1,500、Ultra 2,000；无周额度、无 5h 窗口。重置为太平洋时间午夜（PT midnight），以返回的 resetTime 为准。
  • 官方：REPL 内 /stats model 显示各模型 Usage left % 与重置时间（无 headless 对应物）。
# 逆向查询端点（Gemini CLI / Code Assist 账号）
POST https://cloudcode-pa.googleapis.com/v1internal:retrieveUserQuota
Authorization: Bearer <access_token>   # 来自 ~/.gemini/oauth_creds.json

# 响应按模型分桶：{ modelId, remainingFraction (0–1), resetTime (ISO-8601) }
# 429 错误体另含 quotaResetDelay / quotaResetTimeStamp
注意 第三方模型桶（Claude / GPT-OSS）是池级共享水位，不是单模型精确额度，展示时不要按单模型呈现。v1internal:* 为内部端点，无版本契约保证。
来源 Gemini CLI Quotas & Pricing · Antigravity Statusline 文档 · Antigravity Plans · agy-quota · CodexBar Gemini provider

04 · Cursor

Anysphere
5h 窗口：没有 周额度：没有 月度计费周期：唯一维度

额度结构

  • 2025 年 6 月定价改革后，订阅额度是美元等值金额池而非请求数：Pro $20/月、Pro+ $60、Ultra $200（另有 2026-07 用量翻倍调整）。分 Cursor Models 与 Other Models 两个池，外加可开关的 On-Demand 超额池。
  • 重置：按各账号计费周期周年日重置，精确到具体时刻（billingCycleEnd 为带时分秒的 Unix 毫秒），未用完不结转。
  • 5h 窗口从未采用；与额度无关的并发限速存在（高峰排队变慢，不报错）。

查询方式

  • 官方：cursor.com/dashboard 的 Spending 页；Admin API（api.cursor.com/teams/*）仅企业管理员可用，个人订阅者无官方用量 API。
  • 逆向（个人查询主路径）：与 IDE 本体同一套内部接口：
POST https://api2.cursor.sh/aiserver.v1.DashboardService/GetCurrentPeriodUsage
Authorization: Bearer <accessToken>
Connect-Protocol-Version: 1

# 关键响应字段：
#   billingCycleStart / billingCycleEnd  —— Unix 毫秒，end 即重置时刻
#   planUsage.{totalSpend, remaining, limit, totalPercentUsed}  —— 单位：美分
#   spendLimitUsage —— On-Demand 支出上限用量
  • Token 获取：POST /auth/exchange_user_api_key 用 crsr_... API key 兑换（有效期约 1 小时，需重兑换）；或读本地 ~/.cursor/auth.json（由 agent login 写入）/ IDE 的 state.vscdb 中 cursorAuth/accessToken。
  • 参考实现：cursor-cli-usage（Python，自带缓存与 statusline 模式）、dmwyatt/cursor-usage（Go）。
对监控产品的含义 Cursor 只需监控一个窗口：当前计费周期。展示「已用/上限（美分）+ totalPercentUsed + billingCycleEnd 倒计时」即可完整覆盖。Cursor 不通过 HTTP 响应头暴露额度，429 + Retry-After 仅是网关限流，与订阅额度无关。
来源 Cursor 官方 Usage & Limits · Cursor APIs · cursor-pulse 逆向文档 · dmwyatt 的 Gist

05 · Grok Build

xAI
5h 窗口：没有 周额度：有（唯一主维度） 月度/日度配额：没有

额度结构

  • 2026 年 6 月起付费套餐（SuperGrok / X Premium+）改为一个跨产品共享的周用量池——Chat / Imagine / Voice / Build 全部共用，以百分比计量；xAI 不公布池子绝对大小。
  • 官方明确："Unlike Claude Code and Codex, where you're dealing with 5-hour usage windows, Grok Build runs on a flexible weekly usage pool."
  • 重置：账户级 7 天滚动周期，锚定在账户自身周期（实测 2026-08-17T17:33Z → 2026-08-24T17:33Z，恰好 7 天）；无全球统一重置点。
  • Extra Usage Credits：按美元计的超额付费余额，1 年过期，可 Auto Top Up。

查询方式

  • 官方：CLI /usage（别名 /cost）；grok.com → Settings → Usage（总进度条 + 分产品细分 + 重置时间）。ACP 扩展方法 x.ai/billing 已预留但 stdio 模式未启用。
  • 逆向（多工具在用，目前最可靠）：
GET https://cli-chat-proxy.grok.com/v1/billing?format=credits
Authorization: Bearer <access_token>   # 来自 ~/.grok/auth.json

# 关键响应字段（config 下）：
#   currentPeriod.{type, start, end}  —— end 即重置时间；type 可能为
#     USAGE_PERIOD_TYPE_WEEKLY / _MONTHLY / _DAILY，务必读它防御漂移
#   creditUsagePercent                —— 已用百分比（为 0 时字段省略）
#   productUsage[]                    —— 分产品细分（如 GrokBuild）
#   prepaidBalance                    —— Extra Usage Credits 余额
凭证坑 Grok 的 refresh token 单次使用且每次刷新轮换：第三方工具刷新后必须原子写回 ~/.grok/auth.json，否则官方 CLI 下次刷新会 refresh_token_reused 失败。只读方案（过期则提示用户运行一次 grok login）更安全。轮询建议 ≥60s。
来源 xAI 官方 FAQ · grok.com Release Notes · CodexBar Grok 文档 · aiquokka · TraceCheck 核验页

06 · Claude Code

Anthropic
5h 窗口：有（滚动） 周额度：有（固定时刻） 模型专属周额度：Opus / Sonnet 月度/日度用量配额：没有

额度结构与重置语义

  • 5h 窗口：滚动——从窗口内第一条消息起算，5 小时后整窗重置。
  • 周额度：固定时间点重置，该时刻由系统分配给账户，与订阅开始日、使用时间无关（不是滚动 7 天）；另有 seven_day_opus / seven_day_sonnet 模型专属周窗口（未使用时为 null）。
  • claude.ai 网页/桌面端、IDE 插件、Claude Code 共享同一池子；用 API key 时不走订阅额度。
  • 所有查询渠道都直接返回精确 resets_at 时间戳，无需自己推算，天然规避时区问题。

查询方式（官方 → 逆向）

  • statusline rate_limits 字段（官方文档化，会话内最佳）：~/.claude/settings.json 配置 statusLine.command 后，每次渲染向脚本 stdin 管道 JSON：
"rate_limits": {
  "five_hour": { "used_percentage": 23.5, "resets_at": 1738425600 },
  "seven_day": { "used_percentage": 41.2, "resets_at": 1738857600 }
}
// 仅 Pro/Max 订阅（OAuth）且首个 API 响应后出现；窗口重置后该字段被移除
  • /usage 交互命令：5h 与 weekly 进度条 + 重置倒计时；无官方非交互输出（claude -p "/usage" 打印的是会话摘要）。
  • 逆向 GET https://api.anthropic.com/api/oauth/usage（外部监控最实用）：无需会话运行、服务器端权威数据、跨设备：
GET https://api.anthropic.com/api/oauth/usage
Authorization: Bearer <claudeAiOauth.accessToken>
anthropic-beta: oauth-2025-04-20
User-Agent: claude-code/<version>   # 关键！缺了会落入激进限流桶，持续 429

# 响应：five_hour / seven_day / seven_day_opus / seven_day_sonnet
#   { utilization (0–100), resets_at (ISO-8601 UTC) }；extra_usage 块标识付费超额
  • 凭证：macOS Keychain security find-generic-password -s "Claude Code-credentials" -w；Linux ~/.claude/.credentials.json；或环境变量 CLAUDE_CODE_OAUTH_TOKEN。access token 约 60 分钟过期，由官方 CLI 自动刷新。
  • 被动方式：每个 API 响应携带 anthropic-ratelimit-unified-{5h,7d}-{utilization,reset} 头（2026-03 npm 包源码泄露证实 /usage 读的就是这套头），可经本地代理抓取。
  • 轮询经验值：带正确 UA 时 ≥180s 安全；否则持续 429 且 30 分钟难恢复。Rust 参考实现：claude-usage crate。
合规风险 2026-02 Anthropic 明确将 Free/Pro/Max 的 OAuth token 用于第三方工具列为违反 ToS，并于 2026-04 技术封禁过第三方客户端。只读 usage 属灰色地带，接入前需评估。

07 · Codex CLI

OpenAI
5h 窗口：有（政策反复） 周额度：有（7 天） 月度：仅 Business/Enterprise 日度：没有

额度结构与重置语义

  • 5h 滚动窗口 + 7 天周窗口双维度。⚠️ 政策反复：2026-07-12 曾临时取消 5h 限制，约 2026-08-25 起对 Plus 恢复——必须以 API 实际返回为准，不能硬编码窗口存在。
  • 重置：均为账户锚定滚动窗口——官方原文 "A new window starts when you send your first message in Work or Codex after the previous window ends"；周窗口亦锚定到周期结束后的首次请求，无固定整点、无统一时区。
  • 观测警告：闲置账户的 reset_at 会随轮询向后滑动（始终保持约 7 天后），used_percent 曾数小时内从 55% 掉到 0%——应视为「服务端声明」并保留本地历史。
  • 附加维度：Credits 余额、Code review 独立周窗口、模型专属额度（additional_rate_limits[]）、可囤的重置券（rate_limit_reset_credits）。

查询方式（官方 → 逆向）

  • codex app-server JSON-RPC（半官方，最适合程序化）：codex -s read-only -a never app-server → account/rateLimits/read，返回 primary/secondary 窗口 + reset 时间戳 + credits + plan。CodexBar 即走此路。
  • TUI 命令：/status（5h/周限剩余百分比与重置时间）、/usage、/statusline 可配置状态栏；无 headless --json 输出。
  • 逆向 wham/usage（CLI 自己每 ~60s 就在轮询）：
GET https://chatgpt.com/backend-api/wham/usage
Authorization: Bearer <access_token>      # 来自 ~/.codex/auth.json
ChatGPT-Account-Id: <account_id>

# 响应：plan_type、rate_limit.{primary_window, secondary_window}、credits 等
# 关键陷阱：按 limit_window_seconds 判断窗口类型
#   18000 = 5h，604800 = 7d —— 不要按 primary/secondary 槽位判断！
#   Team 等套餐 primary 就是周窗口，secondary 为 null
  • 被动方式：模型响应头 x-codex-{primary,secondary}-{used-percent,window-minutes,reset-at}、x-codex-plan-type 等（官方在 codex#16323 确认存在；WebSocket 传输下无响应头）。
  • 凭证刷新：POST https://auth.openai.com/oauth/token，client_id=app_EMoamEEZ73f0CkXaXp7hrann。

08 · OhMyC 落地建议

集成优先级

优先级模式适用方备注
首选 官方 statusline JSON 注入 Claude（rate_limits）、Antigravity（quota 桶） 有官方契约，但仅在 CLI 运行时有事件推送
首选 官方/半官方进程接口 Codex app-server JSON-RPC CLI 自带，schema 相对稳定
次选 读本地凭证 + 调内部用量端点轮询 Claude /api/oauth/usage、Codex wham/usage、Grok /v1/billing、Cursor GetCurrentPeriodUsage、Gemini retrieveUserQuota 缓存 ≥3–5 分钟，429 指数退避；容忍 schema 漂移
兜底 被动解析响应头 / 429 错误体 Codex x-codex-*、Claude anthropic-ratelimit-unified-*、Gemini quotaResetTimeStamp 不产生额外请求，但只在有流量时可用

三个跨产品的通用注意点

  1. 重置时间一律以 API 返回的时间戳为准，不要自己推算——各家语义不同：Claude 周额度是固定时刻，Codex / Grok 是账户锚定滚动，Gemini 日额度是 PT 午夜，Kimi 旧套餐按订阅日 7 天。
  2. 凭证刷新要克制：Claude access token 约 60 分钟过期（官方 CLI 自动刷新）、Grok refresh token 单次轮换、Cursor 兑换 token 约 1 小时——「只读 + 过期提示重新登录」比主动刷新更稳；Grok 若自行刷新必须原子写回。
  3. UI 建模差异：Cursor 只有月度池（单位是美分），Grok 只有周窗口（只有百分比），Kimi 新套餐只有 5h 窗口——不要给所有工具预留统一的「5h + 周」双槽位。按三种范式抽象：双窗口 / 单周池 / 单月池。

09 · Statusline 类官方机制对比

Claude Code 的 statusLine 是「CLI 把会话与额度 JSON 经 stdin 推给用户脚本、脚本 stdout 作为状态栏」的官方契约——零逆向、无需轮询。调研其余五家是否有等价物，结论分三层：stdin 直接含额度（Claude、Antigravity）→ 有 command 型 statusline 但不含额度（Kimi、Grok、Cursor）→ 无 command 型但有更强的官方推送（Codex app-server）。

工具command 型 statuslinestdin JSON 含额度额度的官方/半官方替代通道
Claude Code 有 rate_limits（5h/7d 百分比+重置） statusline 本身就是额度通道
Antigravity (agy) 有 quota 桶（remaining_fraction + reset_time） statusline 本身就是额度通道
Kimi Code 有（二进制实证） 没有（model/cwd/git/context 等） 脚本自查 GET /coding/v1/usages（注意 300ms 超时，需本地缓存）
Grok Build 有 没有（文档明确刻意不提供） ACP x.ai/billing（需 grok.com OAuth）
Cursor Agent 有（官方自述与 Claude 对齐） 没有（仅 context_window） 无官方出口，只能逆向 GetCurrentPeriodUsage
Codex 没有（issue 挂 5 个月未实现） — app-server account/rateLimits/read + /updated 事件推送（数据最丰富）

Kimi Code — 有 statusline，但 payload 不含额度（本机二进制实证）

  • 配置写在 ~/.kimi-code/tui.toml 的 [status_line]：command（自定义脚本）与 items（内置槽位：mode, goal, model, tasks, cwd, git, tips）。官方文档暂无条目，证据来自 ~/.kimi-code/bin/kimi 内嵌 bundle。
  • 契约与 Claude 同构：spawn sh -c <command>，stdin 写入 JSON payload，stdout 第一行作为状态栏文本；环境变量 KIMI_CODE_STATUS_LINE=1；300ms 超时、64KB 上限、最小 1s 重跑间隔。
  • payload 字段：{model, cwd, gitBranch, permissionMode, planMode, contextUsage, contextTokens, maxContextTokens, sessionId, version}——无额度字段。但 statusline 脚本可自建缓存调用 /coding/v1/usages，组成「官方注入点 + 接口」的混合方案。

Grok Build — 有 statusline，额度走 ACP

  • ~/.grok/config.toml 的 [ui.status_line]：type = "command" + command + refresh_interval（秒）。stdin JSON（snake_case）含会话成本 cost.total_cost_usd、上下文 context_window.*、git 上下文等，官方文档明确 rate-limit 摘要刻意不提供；300ms 防抖，10s 超时。
  • 额度官方通道是 ACP 扩展方法 x.ai/billing（grok agent stdio）：返回 creditUsagePercent + currentPeriod.{type,start,end}（重置时间）；仅接受 grok.com OAuth 登录，API key 会返回 auth_required。TUI 自己每 30s 轮询此方法，可作轮询节奏参考。

Cursor Agent — 有 statusline（与 Claude spec 对齐），账户额度无官方出口

  • 配置 ~/.cursor/cli-config.json：
{
  "statusLine": {
    "type": "command",
    "command": "~/.cursor/statusline.sh",
    "updateIntervalMs": 300,   // 下限 300ms
    "timeoutMs": 2000
  }
}
  • stdin JSON 含 model、workspace、context_window.{used_percentage, remaining_percentage, total_input_tokens} 等——无账户额度/速率字段；注意自定义 statusline 会整体替换原生 footer（官方确认为有意行为）。
  • agent status --format json 只含认证状态，不含额度；TUI 的 /usage 无 headless 对应物。账户额度唯一路径仍是逆向 api2.cursor.sh。

Codex — 无 command 型 statusline，但有六家中唯一的官方事件推送

  • tui.status_line 只是内置项字符串数组（29 个枚举值），自定义 command 的 feature request（#17827、#20244）至今 open。额度内置项 five-hour-limit / weekly-limit 只渲染 5h 84% left 式百分比，无重置时间（#24080 open）。
  • 内置额度项的轮询器是自适应节流：<75% 每 60s → ≥99% 每 5s。
  • 真正的官方通道是 codex app-server：account/rateLimits/read 拉取 + account/rateLimits/updated 事件推送（额度变化主动通知，含 usedPercent、resetsAt、credits、planType）——数据丰富度超过 Claude statusline，是六家中唯一的官方推送流。
对 OhMyC 的结论 能「零逆向拿额度」的官方通道共 3 条：Claude statusline、agy statusline、Codex app-server 推送。Kimi / Grok / Cursor 的 statusline 机制存在但不含额度——可作为触发器或展示层，额度数据仍需走第 02/04/05 章的接口（Grok 可优先用官方 ACP x.ai/billing）。Cursor 是唯一既无额度 statusline 字段、也无任何官方额度出口的。
