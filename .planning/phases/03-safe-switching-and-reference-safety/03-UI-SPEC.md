## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#080A0A` | App background, page canvas, deepest base surface |
| Secondary (30%) | `#0F1112` | Cards, sidebar, detail panels, dialog backgrounds |
| Accent (10%) | `#5E6AD2` | Switch Profile CTA, active profile badge, focus ring, confirmation primary action |
| Destructive | `#E0675C` | Delete component button, destructive confirmation borders, active-profile-delete-blocked messaging |
| Warning | `#D8AB45` | Pre-flight missing-component warnings, settings overwrite risk, lock-contention errors |
| Success | `#4DA36F` | Deactivation-success feedback, activation-complete confirmation |

Accent reserved for: `Switch to {ProfileName}` CTA in switch confirmation dialog, active-profile name badge, keyboard focus ring, and activation-complete success state. Do not use accent on Cancel or Deactivate buttons.

Warning (`--accent-amber`) reserved for: pre-flight missing-component alerts, settings overwrite warnings inside confirmation dialogs, and file-lock contention errors. This color signals "proceed with caution" but does not block action.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA (switch) | Switch to {ProfileName} |
| Switch confirmation heading | Switch profiles? |
| Switch confirmation body | "{currentActive} is active. Switch to {targetProfile}?" |
| Missing components heading | Cannot activate {ProfileName} |
| Missing components body | This profile references store components that no longer exist. Fix the profile before activating. |
| Missing components list label | Missing components |
| Settings overwrite warning | This profile will overwrite settings you manually configured. |
| Settings overwrite key list label | Affected settings |
| Deactivation feedback | Deactivated {ProfileName} |
| Activation feedback | Activated {ProfileName} |
| Lock contention error | Another activation is in progress. Wait a moment and try again. |
| Active profile delete blocked heading | Cannot delete active profile |
| Active profile delete blocked body | Deactivate {profileName} before deleting it. |
| Empty state heading | No components in this store yet (carried from Phase 01) |
| Empty state body | Import agents, skills, or commands from an existing Claude-compatible directory to start building a canonical local store. (carried from Phase 01) |
| Error state | Could not complete this action. Wait a moment and try again. If the problem persists, check that no other process is modifying profiles. |
| Destructive confirmation (store component) | Delete component: "Delete this store component?"; Referenced component: "This component is still referenced by profiles. Delete anyway?" (carried from Phase 01) |

Additional copy rules:
- Confirmation dialogs name the specific profiles involved, never use generic "this profile" when the name is known.
- Pre-flight warnings use imperative voice: "Fix the profile before activating", not "The profile should be fixed".
- Deactivation feedback uses the past tense: "Deactivated {name}".
- Lock contention copy avoids technical jargon: say "Another activation is in progress", not "Activation lock held by PID".

## Phase 03 Visual And Interaction Contracts

### Confirmation dialog pattern

All confirmation dialogs in this phase share a single modal structure to maintain visual consistency with the existing `DeleteConfirmDialog`:

- **Overlay:** `fixed inset-0 bg-black/60 flex items-center justify-center z-50`
- **Container:** `p-6 max-w-md w-full mx-4 space-y-4` with `bg-[var(--surface-raised)]` border `var(--border-default)`, `rounded-[var(--radius-xl)]`
- **Heading:** `text-lg font-semibold text-[var(--text-primary)]`
- **Body text:** `text-[13px] text-[var(--text-secondary)]`
- **Warning block:** `bg-[var(--accent-amber)]/10 border border-[var(--accent-amber)]/30 rounded-[var(--radius-md)] p-3` with amber text for warnings
- **Cancel button:** Secondary style -- `bg-[var(--surface-overlay)] text-[var(--text-secondary)]`, `hover:bg-[var(--border-hover)]`
- **Primary action button:** Accent blue style -- `bg-[var(--accent-blue)] text-white`, `hover:bg-[var(--accent-blue-hover)]`
- **Destructive action button:** Red style -- `bg-[var(--accent-red)] text-white`, `hover:bg-[var(--accent-red)]/90`
- **Button order:** Cancel (left) then primary/destructive (right), right-aligned via `flex justify-end gap-2`
- **Motion:** No entrance/exit animation on dialogs themselves. Match the existing `DeleteConfirmDialog` pattern.

### Switch confirmation dialog (ConfirmSwitchDialog)

When a user clicks `Activate` on a profile while another profile is already active, a confirmation dialog must appear before any filesystem changes.

- **Trigger:** User clicks `Activate` on a non-active profile when `currentActive` is not null.
- **Heading:** "Switch profiles?"
- **Body:** "{currentActive} is active. Switch to {targetProfile}?"
- **Pre-flight section (conditional):** If the pre-flight check returns settings overwrite warnings, render a warning block below the body listing the affected setting keys. If the pre-flight check returns missing components, render an amber warning block with the heading "Missing components" and a bulleted list of missing item names. In this case the primary CTA changes to disabled with text "Fix missing components first".
- **Primary CTA:** "Switch to {targetProfile}" in accent blue.
- **Cancel CTA:** "Cancel" in secondary style.
- **No destructive styling needed** -- switching is reversible.

### Activation confirmation dialog (ActivateConfirmDialog)

When a user clicks `Activate` on a profile while no other profile is active, and the pre-flight check returns settings overwrite warnings, a confirmation dialog appears.

- **Trigger:** User clicks `Activate` on a profile when no profile is active, and pre-flight returns non-empty `settingsWarnings`.
- **Heading:** "Activate {targetProfile}?"
- **Body:** "This profile will overwrite settings you manually configured."
- **Warning block:** Amber styling listing each affected setting key.
- **Primary CTA:** "Activate {targetProfile}" in accent blue.
- **Cancel CTA:** "Cancel" in secondary style.
- **When no warnings:** No dialog is shown. Activation proceeds directly.

### Missing components blocking state (ActivationBlockedDialog)

When a user clicks `Activate` and pre-flight returns missing components, activation is blocked entirely.

- **Trigger:** Pre-flight check returns `canActivate: false` with non-empty `missing` array.
- **Heading:** "Cannot activate {profileName}"
- **Body:** "This profile references store components that no longer exist. Fix the profile before activating."
- **Warning block:** Amber styling with label "Missing components" and a bulleted list of each missing item formatted as its type:name (e.g., "agent:code-review", "skill:refactoring").
- **Primary CTA:** None. The dialog has only a "Close" button in secondary style.
- **Alternative:** The user must edit the profile to remove missing references before activating.

### Deactivation behavior

- **No confirmation dialog.** Deactivation is immediate and direct (source: `03-CONTEXT.md`).
- The `Deactivate` button on `ProfileCard` triggers the mutation directly.
- After successful deactivation, show a success toast/message: "Deactivated {profileName}".
- The `ProfileCard` UI transitions from showing `Deactivate` to showing `Activate` on the now-inactive profile.

### Active profile deletion protection

- When a user clicks `Delete` on the currently active profile, instead of the normal delete dialog, show a blocking message.
- **Heading:** "Cannot delete active profile"
- **Body:** "Deactivate {profileName} before deleting it."
- **Primary CTA:** None. The dialog has only a "Close" button in secondary style.
- The `Delete` button remains visible but triggers this protection dialog instead of the normal delete flow.

### Lock contention error

- If the activation request fails due to a held file lock, display an error toast at the action point.
- **Copy:** "Another activation is in progress. Wait a moment and try again."
- Use the warning (`--accent-amber`) color for the error indicator, not destructive red, because this is a transient condition.
- No dialog needed -- a toast or inline error message near the Activate button is sufficient.

### Inline profile reference display in store browser (INV-03)

The existing `StoreComponentList` already computes a `referencedByMap` and shows a numeric reference count with a tooltip. Phase 3 upgrades this to inline profile name display.

- Replace the numeric-only "profile reference count" column cell with the count plus inline profile names.
- **When 0 references:** Show "0" in `text-[var(--text-tertiary)]`, no additional display.
- **When 1-2 references:** Show the profile names directly as small chips/tags. Each chip: `rounded bg-[var(--accent-blue)]/8 px-1.5 py-0.5 text-[11px] text-[var(--accent-blue)] border border-[var(--accent-blue)]/15`. This matches the existing `RuntimeGroup` chip pattern from `ProfileCard.tsx`.
- **When 3+ references:** Show the count as "Used by N profiles" in `text-[13px] text-[var(--accent-blue)]` with a tooltip listing all profile names on hover. This prevents row overflow.
- **Column header:** Change "profile reference count" to "profiles" for brevity.
- **Reference data source:** Continue using the existing client-side `referencedByMap`. The server-side `getReferencingProfiles()` is optional enrichment.
- **Delete interaction:** The existing `DeleteConfirmDialog` warn-but-allow pattern is preserved. The inline display ensures the user sees references before clicking delete.

### ProfileCard action button states (evolved)

The existing `ProfileCard` button bar evolves for Phase 3 safety:

- **When profile is active and user clicks Delete:** Opens the "Cannot delete active profile" blocking dialog instead of the normal delete confirmation.
- **When profile is not active, another profile is active, and user clicks Activate:** Opens the switch confirmation dialog.
- **When profile is not active, no profile is active, and user clicks Activate:** Proceeds directly if no warnings; opens activation confirmation if settings warnings exist; opens blocking dialog if missing components.
- **When profile is not active, no profile is active, no warnings, no missing:** Activate directly with no dialog.
- Button styling remains unchanged from Phase 2: Activate in accent blue, Deactivate in secondary, Delete in red tint.

### Motion and states (carried forward)

- Preserve the repo's existing restrained motion style: opacity/transform only, 150-200ms max.
- Confirmation dialogs do not animate in/out -- match the existing `DeleteConfirmDialog`.
- Hover should slightly raise contrast or border visibility; no layout shift.
- Focus state is always a 2px outline/ring in accent blue with 2px offset.
- Disabled controls use 50% opacity and `not-allowed` cursor.
- Success feedback (deactivation toast, activation toast) uses `--accent-green` color.

### Accessibility

- All confirmation dialogs must trap focus within the dialog container.
- Escape key must close/cancel the dialog.
- The dialog overlay must have `aria-modal="true"` and `role="dialog"` or `role="alertdialog"`.
- Dialog heading must use an `aria-labelledby` pattern linking to the heading element.
- Profile name chips in the store browser must be readable by screen readers as "{name} profile" via `aria-label`.
- Icon-only controls require an `aria-label`.

### Error handling at action point

- Activation errors (lock contention, pre-flight failure, rollback) appear inline near the profile card or as a toast anchored to the action, not as a detached global notification.
- Rollback errors after a failed activation should surface as a warning: "Activation failed. Your previous environment has been restored." using `--accent-amber`.
- Deactivation errors surface at the ProfileCard: "Deactivation failed. Check for file lock conflicts."
