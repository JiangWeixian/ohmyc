## Phase 7 Visual And Interaction Contracts

### Model Config Env Var Preview Section (shared by both dialogs)

A conditional section rendered inside `ActivateConfirmDialog` and `ConfirmSwitchDialog` when the preflight result includes `modelConfigChanges`.

**When to render:** Only when `modelConfigChanges` is present and `changes.length > 0`. When the profile has no model config, this entire section is omitted -- no "Model Config: None" placeholder.

**Layout:** Inline info block inserted after the existing body text and before the existing warning blocks (or after warning blocks, as space permits).

- Container: `bg-[#5E6AD2]/8 border border-[#5E6AD2]/15 rounded-[var(--radius-md)] p-4`
  - Uses accent-blue at very low opacity for the background (not amber -- this is informational, not a warning)
  - Matches the RuntimeGroup chip pattern from ProfileCard.tsx (same blue-tinted container)
  - Padding uses `p-4` (16px) to align with the declared spacing scale (sm token)
- Header line: `text-[#5E6AD2] text-[13px] font-semibold mb-1`
  - Text: "Model Config: {configName}"
- Env var list: `<ul>` with `text-[13px] font-mono`
- Each list item:
  - Action prefix: `text-[var(--accent-amber)] font-semibold` -- SET, CHANGE, or REMOVE
  - Space separator
  - Key=value: `text-[var(--text-secondary)]`
  - For CHANGE items: previous value shown in `text-[var(--text-tertiary)]` after the value in parens
  - For REMOVE items: key only, no value

**Example rendering:**

```
Model Config: work-anthropic
  SET ANTHROPIC_API_KEY=****a1b2
  SET ANTHROPIC_BASE_URL=https://api.anthropic.com
  SET ANTHROPIC_MODEL=claude-3-opus
```

For CHANGE (existing env vars):
```
  CHANGE ANTHROPIC_API_KEY=****c3d4 (was: ****a1b2)
  CHANGE ANTHROPIC_BASE_URL=https://custom.proxy.io
```

For REMOVE (switch dialog, deactivating profile's model config):
```
  REMOVE ANTHROPIC_API_KEY
  REMOVE ANTHROPIC_BASE_URL
  REMOVE ANTHROPIC_MODEL
```

### ActivateConfirmDialog Extension

The existing `ActivateConfirmDialog` gains an optional `modelConfigChanges` prop.

**Props change:**
```typescript
interface ActivateConfirmDialogProps {
  targetProfile: string;
  settingsWarnings: string[];
  modelConfigChanges?: ModelConfigPreview; // NEW
  onConfirm: () => void;
  onCancel: () => void;
}
```

**Rendering order:**
1. Heading: "Activate {targetProfile}?"
2. Body: "This profile will overwrite settings you manually configured."
3. Model config section (if `modelConfigChanges` present)
4. Affected settings warning block (if `settingsWarnings` non-empty)
5. Button row: "Don't Activate" + "Activate {targetProfile}"

**Visual:** The model config section uses blue-tinted container (#5E6AD2/8 background with /15 border), distinct from the amber warning block, to convey "informational preview" rather than "caution."

### ConfirmSwitchDialog Extension

The existing `ConfirmSwitchDialog` gains optional `modelConfigChanges` prop. For switch scenarios, the preflight result may include both deactivation changes (from the current profile) and activation changes (from the target profile).

**Props change:**
```typescript
interface ConfirmSwitchDialogProps {
  currentActive: string;
  targetProfile: string;
  missing: string[];
  settingsWarnings: string[];
  modelConfigChanges?: ModelConfigChanges; // NEW -- may contain both deactivation and activation
  onConfirm: () => void;
  onCancel: () => void;
}
```

**Rendering order:**
1. Heading: "Switch profiles?"
2. Body: "{currentActive} is active. Switch to {targetProfile}?"
3. Deactivation model config section (if current profile has model config)
   - Header: "Deactivating {currentActive}:"
   - Lines: REMOVE for each env var from current profile's model config
4. Activation model config section (if target profile has model config)
   - Header: "Activating {targetProfile}:"
   - Lines: SET or CHANGE for each env var from target profile's model config
5. Missing components warning block (if `missing` non-empty, CTA disabled)
6. Affected settings warning block (if `settingsWarnings` non-empty)
7. Button row: "Keep Current" + "Switch to {targetProfile}"

**Deactivation section styling:** Same blue-tinted container as activation, but with REMOVE lines only. No separate "deactivation" color -- REMOVE uses amber prefix, same as SET/CHANGE.

**Switching from profile WITH model config to profile WITHOUT:** Shows only the deactivation section with REMOVE lines. No activation section.

**Switching from profile WITHOUT to profile WITH:** Shows only the activation section with SET lines. No deactivation section.

**Switching between two profiles both WITH model configs:** Shows both sections -- deactivation REMOVE lines first, then activation SET/CHANGE lines.

### ProfileCard Data Flow Change

`ProfileCard.tsx` must pass `modelConfigChanges` from the preflight result to the dialog components.

**Change in rendering:**
```tsx
{dialogState?.type === 'switch' && (
  <ConfirmSwitchDialog
    currentActive={dialogState.preflight.currentActive!}
    targetProfile={profile.name}
    missing={dialogState.preflight.missing}
    settingsWarnings={dialogState.preflight.settingsWarnings}
    modelConfigChanges={dialogState.preflight.modelConfigChanges} // NEW
    onConfirm={() => { onActivate(); setDialogState(null); }}
    onCancel={() => setDialogState(null)}
  />
)}

{dialogState?.type === 'activate-warn' && (
  <ActivateConfirmDialog
    targetProfile={profile.name}
    settingsWarnings={dialogState.preflight.settingsWarnings}
    modelConfigChanges={dialogState.preflight.modelConfigChanges} // NEW
    onConfirm={() => { onActivate(); setDialogState(null); }}
    onCancel={() => setDialogState(null)}
  />
)}
```

### PreflightResult Type Extension

Both backend and frontend `PreflightResult` interfaces gain the `modelConfigChanges` field.

```typescript
interface ModelConfigEnvChange {
  action: 'SET' | 'CHANGE' | 'REMOVE';
  key: string;
  value: string;          // masked for API key, plain for others
  previousValue?: string;  // only for CHANGE action
}

interface ModelConfigChanges {
  configName: string;
  changes: ModelConfigEnvChange[];
  // For switch dialogs -- deactivation changes from current profile
  deactivationChanges?: ModelConfigEnvChange[];
  deactivationConfigName?: string;
}
```

**Backend type location:** `packages/cli/src/server/services/profileService.ts` PreflightResult interface
**Frontend type location:** `packages/ui/src/hooks/useProfiles.ts` PreflightResult interface

### Backend Env Var Injection (ProfileService.activate Step 10)

No visual contract -- this is a backend change. Documented here for completeness:

After the existing settings merge (Step 10), before writing settings.json:
1. Check if `profile.modelConfig` is set
2. Load model config via `ModelConfigService.get(name)`
3. If found, build env vars: `ANTHROPIC_API_KEY`, `ANTHROPIC_BASE_URL`, optionally `ANTHROPIC_MODEL`
4. Spread into `merged.env`: `merged.env = { ...(merged.env || {}), ...envVars }`
5. If model config not found (deleted between preflight and activation), skip silently -- proceed without env vars

### Deactivation Behavior

No visual contract changes. Deactivation remains immediate with no confirmation dialog (Phase 3 pattern). The existing per-profile backup mechanism restores settings.json including env field automatically. No new deactivation code needed.

### Long URL Truncation

For `ANTHROPIC_BASE_URL` values exceeding 40 characters in the preview, apply middle truncation:
- Show first 20 chars + `...` + last 15 chars
- Example: `https://very-long-api-proxy.../v1/anthropic`
- This applies to the preview display only, not to the actual value written to settings.json

## States

### Loading State
No change from existing patterns. Preflight mutation shows "Checking..." on the Activate button during preflight.

### Model Config Deleted Between Preflight and Activation
- Backend handles gracefully: skip env var injection, proceed with activation
- No special UI state needed -- the activation succeeds without model config env vars
- Consider logging a warning server-side for debugging

### Profile with No Model Config
- No model config section appears in either dialog
- Activation and switching behave exactly as before Phase 7
- `modelConfigChanges` is undefined in preflight response

### Profile with Model Config, All Env Vars New (SET)
- Model config section shows all lines with SET prefix
- Blue-tinted container, amber action prefixes

### Profile with Model Config, Some Env Vars Existing (CHANGE)
- Model config section shows CHANGE prefix for existing keys
- Previous value displayed in tertiary text color after the new value
