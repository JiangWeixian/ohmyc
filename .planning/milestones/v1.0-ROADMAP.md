# Roadmap: ClaudeUI

## Overview

ClaudeUI will evolve from a useful Claude configuration browser into a reliable local manager for reusable Claude components and working profiles. The roadmap starts by making the store and inventory model trustworthy, then adds profile composition on top of that foundation, and finally hardens profile switching so advanced users can activate and change environments with confidence.

## Phases

**Phase Numbering:**
- Integer phases (1, 2, 3): Planned milestone work
- Decimal phases (2.1, 2.2): Urgent insertions (marked with INSERTED)

- [x] **Phase 1: Store and Inventory Foundation** - Make the local store and current-environment inventory trustworthy and source-aware
- [ ] **Phase 2: Profile Composition** - Let users build and inspect reusable Claude profiles from store-managed components

## Phase Details

### Phase 1: Store and Inventory Foundation
**Goal**: Establish the local store as the canonical source of reusable Claude components and expose the current environment with clear source labeling.
**Depends on**: Nothing (first phase)
**Requirements**: [STORE-01, STORE-02, STORE-03, STORE-04, STORE-05, STORE-06, INV-01, INV-02]
**Success Criteria** (what must be TRUE):
  1. User can import Claude-compatible agents, skills, and commands into the local store from an existing directory.
  2. User can browse store-managed components by type and understand their import provenance.
  3. User can inspect current AGENT_HOME components and see whether each item is local, profile-linked, or plugin-provided.
  4. User can inspect installed plugins and Claude-related environment configuration from the current setup.
**Plans**: 4 plans

Plans:
- [x] 01-00-PLAN.md — Add packages/ui test infrastructure and Phase 1 UI behavior suites
- [x] 01-01-PLAN.md — Harden store import contracts, overwrite preview flow, and provenance tracking
- [x] 01-02-PLAN.md — Build source-aware inventory badges plus read-only plugin/config inspection views
- [x] 01-03-PLAN.md — Wire the unified store browser, import dialog, and CRUD UX to the canonical store API

### Phase 2: Profile Composition
**Goal**: Let users compose reusable Claude profiles from store-managed components and inspect what each profile contains before activation.
**Depends on**: Phase 1
**Requirements**: [PROF-01, PROF-02, PROF-03, PROF-04, ACT-01, ACT-02]
**Success Criteria** (what must be TRUE):
  1. User can create and edit named profiles using store-managed agents, skills, commands, plugins, and configuration overlays.
  2. User can inspect a profile's included components and metadata before activation.
  3. User can see which profile is currently active from the UI and API.
  4. Activating a profile creates Claude-compatible generated files and links store-managed components into the expected profile structure.
**Plans**: 3 plans

Plans:
- [x] 02-01-PLAN.md — Normalize active-profile backend semantics and lock activation artifact/link behavior
- [x] 02-02-PLAN.md — Restructure the profile editor into the approved single-page composition flow
- [ ] 02-03-PLAN.md — Build the activation-readiness detail UI and verify active-state presentation end to end

### Phase 3: Safe Switching and Reference Safety
**Goal**: Make profile lifecycle operations safe, reversible, and trustworthy for daily environment switching.
**Depends on**: Phase 2
**Requirements**: [INV-03, ACT-03, ACT-04, ACT-05, ACT-06]
**Success Criteria** (what must be TRUE):
  1. User can deactivate the active profile and recover the prior settings state without manual cleanup.
  2. User can switch directly between profiles without ending up in a partially applied environment.
  3. User receives clear warnings when activation skips missing components or would apply risky changes.
  4. User can see which profiles reference a store component before deleting or changing it.
**Plans**: 2 plans

Plans:
- [ ] 03-01: Implement transaction-like activation, deactivation, switching, and rollback handling
- [ ] 03-02: Add warning surfaces, reference checks, and management safety UX
