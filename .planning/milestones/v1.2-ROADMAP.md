## Phase Details

### Phase 5: Model Config Store Backend
**Goal**: Users can create, read, update, and delete model configs through the API with proper validation and reference protection
**Depends on**: Phase 4 (existing store/profile infrastructure)
**Requirements**: STORE-06, STORE-07, STORE-08, STORE-11
**Success Criteria** (what must be TRUE):
  1. User can create a new model config via API with name, API key, base URL, model name, and provider fields and have it persisted to disk
  2. User can edit any field of an existing model config and the changes are saved
  3. User can delete a model config that is not referenced by any profile
  4. User cannot delete a model config that is referenced by one or more profiles and receives a clear error explaining why
  5. Base URL and model name fields accept any string value per deferred STORE-11 (validation deferred to future release)
**Plans**: 2 plans

Plans:
- [ ] 05-01-PLAN.md -- Shared Zod schemas, ProfileSchema extension, ModelConfigService with TDD tests
- [ ] 05-02-PLAN.md -- StoreService reference checking, provenance extension, CRUD routes with delete protection

### Phase 6: Model Config UI and Profile Integration
**Goal**: Users can manage model configs through the web UI and assign exactly one model config to a profile
**Depends on**: Phase 5
**Requirements**: STORE-09, STORE-10, PROF-05, PROF-06, PROF-07
**Success Criteria** (what must be TRUE):
  1. User sees model configs listed as a tab or section in the store UI alongside agents, skills, and commands
  2. API keys appear masked in both the list view and the edit form, showing only the last 4 characters
  3. User can pick exactly one model config from a dropdown/picker in the profile editor
  4. Profile detail view displays the assigned model config's name and key fields (provider, model name, masked API key, base URL)
  5. Deleting a model config that is referenced by a profile is blocked in the UI with a message showing which profiles reference it
**Plans**: 2 plans

Plans:
- [ ] 06-01-PLAN.md -- API key masking utility, React Query hooks, ModelConfigEditor, store listing extension, sidebar navigation, routing
- [ ] 06-02-PLAN.md -- Profile editor model config dropdown, profile detail model config badge

### Phase 7: Activation Integration
**Goal**: Activating a profile with a model config applies the correct environment variables and users can preview changes before committing
**Depends on**: Phase 6
**Requirements**: ACTV-03, ACTV-04, ACTV-05
**Success Criteria** (what must be TRUE):
  1. Activating a profile that has a model config writes ANTHROPIC_API_KEY, ANTHROPIC_BASE_URL, ANTHROPIC_MODEL, and provider flags to the settings.json env field
  2. Deactivating a profile removes the model-related environment variables from settings.json and restores any previous values that were overwritten
  3. The preflight/preview step shows exactly which environment variables will be set, changed, or removed before the user confirms activation
**Plans**: 2 plans

Plans:
- [ ] 07-01-PLAN.md -- Backend preflight modelConfigChanges computation, activate() env var injection, tests
- [ ] 07-02-PLAN.md -- Frontend PreflightResult type extension, dialog model config sections, ProfileCard wiring
